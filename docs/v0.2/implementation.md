# Loki 0.2 implementation progress

This record distinguishes delivered source from final product acceptance. The final validation phase in [plan.md](plan.md) remains pending.

## Delivered source

- `internal/tools`: module and capability declarations, deterministic private/public dependency resolution, current-state invocation authorization, execution-host configuration, release catalog/artifact identities and owned operation transitions.
- `cmd/loki-manager`: portable management entrypoint for management-only initialization, trusted catalog acquisition, multiple selected-tool installation, independent activation, removal/recovery and execution-host relay. `tools update --catalog FILE` prepares every retained installation and its private closure before switching the release in one state update. Status reports desired exposure and unobserved readiness; doctor checks owned resources, interrupted operations, private dependencies and managed browser binaries. Optional capabilities can be explicitly cleared. Release packaging will install it as `loki`.
- `internal/management`: platform kernel mutation locks, atomic state updates, bounded strict state and complete transaction journals, exact download length/checksum and trusted module metadata checks, bounded traversal/special-file rejecting extraction, owned immutable generations and installation journal recovery. Multi-tool acquisition prepares resources without changing active pointers, then commits one complete configuration snapshot. Recovery compares complete before/after snapshots and owned manifests; incomplete transactions block activation/removal until recovery. Activation validates the whole selected configuration, prerequisite removal is rejected while dependents remain installed, and downloads report elapsed time even while waiting for response bytes. Shared kernel leases protect generations used by active sessions; removal requires those sessions to disconnect, while updates retain older leased generations.
- `modules/browser`: pinned official Playwright and Chrome DevTools Node workspace, bounded strict managed runtime metadata, project/engine/session profile separation, retained output directories and explicit unsafe server-code capability. Doctor launches actual bundled Chrome through bundled Playwright with the sandbox enabled, checks the running version, and closes the owned process tree. Startup is gated until process ownership attaches. Windows readiness does not depend on GUI `--version` output. Playwright sessions explicitly enable the sandbox, and inherited Node module/config overrides are removed.
- `internal/transport/toolproxy`: upstream tool schemas/results, cancellation, progress-token mapping, roots propagation, discovery refresh and fresh invocation gates. Multiple official engines share a server through distinct binding owners and reject name collisions. `tools serve browser --engine both` prepares separate Playwright/DevTools profiles and result directories. `loki_browser_files` lists owned results, reads files/inline images, and stages base64 uploads for the official browser upload tools. MCP resource templates expose those session files with fresh authorization. Transfers are limited to 4 MiB per file; listings are bounded to 4,096 files. Engine roots retain their owned output directory when client roots change. Disabling or replacing the browser rejects cached file/resource calls and refreshes discovery. Owned engine sessions use process groups on Linux/macOS and Job Objects on Windows.
- `scripts/maintainer/v02`: native browser artifact producer source binds local vendor archives to independently trusted version/URL/length/checksum receipts, retains notices and npm dependencies, materializes dependency links, and emits normalized ZIP/module/runtime/catalog metadata. macOS Chrome app links retain their relative vendor spelling, with signature checks before and after copying. Native macOS browser ZIP extraction scopes links to the same Chrome app, writes files before creating aliases, and rejects escape, cycles, dangling links and alias-traversing archive writes. Other archives retain the regular-file/directory contract. It has not been run to produce a candidate; native acquisition recipes and installed signature acceptance remain pending.
- Portable management publication supports `install --bin-dir PATH`, checks existing command ownership, copies the native binary through journaled staging, and recovers interruptions on either side of binary publication. OS installers publish management only and make PATH changes explicit. Native manager producer source bundles exact Go dependency notices and integrity receipts. The manual native workflow separates artifact preparation from final validation on Linux, Windows and macOS; its packaged acceptance uses temporary command/state directories.
- `tools prune TOOL --keep COUNT` retains the current generation, leased programs and the requested number of additional inactive generations. It ignores unknown directories and preserves tool/provider/user data. Verified generation metadata and an atomic move to journal-owned trash make partial deletion recoverable. Runtime ownership errors and actual busy leases are reported separately.
- Runtime doctor probes hold generation leases until they finish, so removal or pruning cannot discard a running diagnostic's binaries. The portable CLI announces resource inspection and managed browser startup on stderr while keeping the structured report on stdout.
- `modules/git`: repository controllers, bounded execution adapters and signing services. `modules/workspace` consumes a repository adapter for operations that need Git.
- `modules/github`: provider implementation and an independent encrypted credential store used by runtime key/user-token operations. Application secrets remain in `modules/secrets`; existing reserved-profile guards protect retained data.
- `modules/execution`, `modules/sharing`, `modules/coordination`: source ownership and corresponding import paths moved together. Coordination embeds the approved command subset generated from devtools 0.23.0 protocol 6.
- Selected MCP/runtime factories now conditionally create module resources and registrations. Workspace reads and ordinary edits use the shared `internal/workcommand` contract and can initialize without a repository, runtime, executor or credentials. An explicit empty tools list creates no workspace resources. Coordination, secrets, GitHub credentials, general job/toolchain resolution and sharing stores are initialized for their selections. GitHub Personal Projects user authorization and its administrative operations additionally require `PersonalProjects` in the runtime layout.
- `internal/tools.BindingSet` owns static and discovered tool names plus a separate resource namespace. `internal/config.ToolGate` reads host-published activation/capabilities for each invocation, with bounded strict inputs and pinned release/mode. Static discovery watches activation; cached calls independently recheck it. The official transport forwards the protected browser service's owned file templates and original contents with fresh resource authorization.
- Full-mode official browser source uses a distinct non-root role, verifies Unix peer identities before MCP initialization, and routes Chrome through the administrator-owned proxy. The MCP HTTP adapter gives each stateful client a separate protected service connection; the browser role creates separate engine profiles/results for that connection. A bounded eight-session pool closes engines when the client session ends, after abandoned initialization, or at application shutdown. Browser HTTP sessions have a 20-minute idle timeout. Container layout/mount/network publication remains composition work.
- `tools configure --mode project-host|full` selects the acquisition contract before tools are installed. Full mode requires a Linux execution host, including an explicitly selected WSL/SSH host. Mode changes reject populated installations and preserve retained user data. Browser producer source accepts native Linux full artifacts as a separate identity.
- Browser readiness additionally records a short local-page video with bundled Playwright/FFmpeg, closes it and removes its temporary files. This covers the pinned default catalog's video prerequisite; actual execution remains a final check.
- Full desired-deployment planning resolves enabled selections and their immutable private program closure, separates public groups from executor prerequisites, assigns service identities/network classes/data owners, and activates Git signing only through the Git capability. `tools plan` emits this credential-free plan. - Native browser input acquisition source fixes the primary Node/Chrome/FFmpeg locations per native target, requires independently trusted length/checksum receipts, streams bounded downloads with progress, and writes a separate assembly recipe. macOS arm64 uses its architecture-specific FFmpeg archive. - Runtime operations independently recheck activation, private resource closure and optional Personal Projects authorization. - The host's atomic activation snapshot lives in its credential-free `control` directory, with bounded regular-file reads. Full program generation roots permit traversal by distinct service identities; archive files retain normalized read/execute permissions and deployment must mount them read-only.
- Full deployment reservations persist the exact program generations before service creation. Removal/pruning remains blocked after a manager crash or exit until the owned backend confirms every reserved resource is absent. Corrupt reservation records also prevent deletion. - Full archives now declare `full-runtime.json`, binding module identity, native target, scoped executable/assets and digest-pinned owned service/workload images to the trusted archive. The full module producer prepares native Go workers and reviewed vendor inputs with integrity, images and notice receipts; it has not built a candidate. Workload images declare their selected Git programs and managed toolchain shims, while browser system libraries are a reviewed separate closure. No image or module candidate has been built yet.

## Remaining implementation

Source implementation now includes module-specific readiness probes, native
management installers/producers, selected factories, protected browser sessions,
full lifecycle and stdio serving, managed endpoint routing, generation pruning,
portable relays, native frontend GitHub setup, plugin/help documentation,
release transactions and session file/image transfer. Source delivery is
recorded separately from final acceptance. Candidate assembly and remaining
native input acquisition are the next workstream phase. Browser profiles whose
engine absence cannot be established are conservatively retained after an abrupt
manager death; user results are retained. Native workflow jobs have not run;
platform availability is not an accepted support claim.

Linux amd64 preparation inputs now include exact GitHub CLI/devtools source
commits, Node/Chrome/FFmpeg archive receipts and the official ripgrep release
asset receipt. Ubuntu package acquisition authenticates signed repository
indices in private APT state and resolves dependencies against empty installed
state. It downloads only receipt-bound packages; no package installation or
maintainer scripts run. Native closure producers preserve notices and limit
extraction to declared paths, including administrator-owned public CA inputs.
Other native architectures prepare their own artifacts on their release runners.

## Final checks

Browser diagnostic fixtures cover exact running-version responses,
trailing/unexpected probe data, bounded pipe draining and inherited module/config
override removal. Framework fixtures cover preserved version aliases and rejected
escape/dangling/cyclic graphs, generic extraction denial and alias-traversing
writes in either archive order. On macOS, doctor verifies the installed Chrome
vendor seal before launching it. Actual native startup, signatures and sandbox
acceptance remain final checks.

Additional final-phase fixtures cover generation retention with current/leased
resources and user data present, recovery after partial trash deletion, native
command ownership protection, and interruption between binary and ownership
marker publication. The native packaged acceptance fixture invokes OS installers
with temporary command/state directories and validates the exact receipt-bound
binary; it has not run.

Tests and architecture/native/protocol/authority/install acceptance run after implementation and candidate preparation. New fixtures cover host/selection constraints, artifact identity/trust inputs, operation transitions, archive traversal/symlink denial, concurrent mutation locks, failed multi-tool acquisition preserving the complete previous snapshot, whole-release updates preserving activation/capabilities, interruption on either side of atomic commit, concurrent generation leases, desired versus observed readiness, private prerequisite failures/removal, disabled binding collisions, discovery collisions, owned MCP file/resource transfer and cached-call denial, vendor link materialization, unsafe browser gates (including the pinned `browser_run_code_unsafe` name), and provider encryption/address isolation. The source extraction retains existing behavior tests. No 0.2 product acceptance pass is claimed here.
